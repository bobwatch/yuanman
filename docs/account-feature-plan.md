## 1. 背景与问题定义

现状（基于代码事实，均附位置）：

1. **支付方式是"一次性标签"，不是数据实体。** 每条记录存自由文本 `paymentMethod`（RecordEntity.kt:36），支出时叫"支付方式"、收入时叫"入账账户"（AddEditRecordScreen.kt:577-581），但底层是**同一个字段**。选项来自两套互相不一致的硬编码列表：支出 7 项（含"花呗/白条"）、收入 6 项（含"微信零钱""投资理财"）（PaymentMethod.kt:13-14），另有 QuickEntryParser.kt:27-39 的别名表是第二份重复硬编码源。
2. **用户无法回答三个真实问题**：①"我这个月信用卡/花呗到底刷了多少"；②"我现在手里总共还有多少钱可花"；③"微信账单和我记的账对不对得上"（对账）。统计页完全没有账户/支付方式维度（stats 包对 paymentMethod 零引用）。
3. **脏数据无法收敛**：CSV 导入对未知支付方式字符串（如"储蓄卡""招行"）原样入库（CsvImportUtils.kt:148,158），今后只会越来越多。
4. **"账户"Tab 已占位**（AccountScreen.kt，文案"支付方式与账户管理即将上线"），底部导航已预留入口。
5. 数据层完全没有余额/资产/负债概念；"balance"只是当期收入减支出的临时计算（HomeViewModel.kt:171-177）。
6. 全部数据链路（CSV、DB 快照备份、JSON 交换格式、双机 WiFi 同步）围绕 records+categories 展开；其中 **DB 快照备份（DatabaseBackupManager，设置页"立即备份/从备份恢复"）是文件级拷贝，自动覆盖新表新列，零改动**；JSON 格式（JsonBackupUtils）主要作为设备同步的线路格式。

结论：账户不是新功能，是**既有"支付方式"概念的升级换代**——从"每笔记录随手打的字符串标签"升级为"用户可管理、跨记录一致、带余额语义的账户对象"。时机成熟且**当前正是做破坏性重构的最后窗口**：v0.0.3 尚属开发期，没有必须永久兼容的外部生态。

## 2. 产品定位

### 一句话定位

> 把散落在每笔记录里的"支付方式/入账账户"字符串，升级为**用户完全自定义的账户体系**（账户与账户类型均为用户自己的数据），并让用户第一次能回答"钱在哪、还剩多少、对没对上"；同时严格不破坏本 App"轻快记账"的核心体验。

### 定位原则（约束后续所有设计决策）

- P0 **不打断记账流**：记一笔默认零次或一次额外点击（账户记忆，见 §6.3）；账户页是"看"的地方，不是记账必经之地。
- P0 **口径一致**：转账必须被预算、统计、小组件、CSV、同步统一理解，不允许"这里算了那里没算"。
- P0 **代码不做账户类型语义**：账户类型是用户的自定义标签，只用于展示与分组；业务逻辑对每个账户一视同仁。唯一允许的语义区分是**记录类型**（EXPENSE/INCOME/TRANSFER，管收支统计口径）。任何"因账户类型不同而行为不同"的需求需重新评审，默认不做。
- P0 **不堆兼容屎山（开发期原则）**：schema、实体、JSON 格式不留弃用字段与废弃路径；能一次做干净的（表重建、格式升级）就一次做干净。**仅对"用户手里真实存在的文件"（老 CSV 导出件）保留导入兼容，且以通用规则实现，不产生独立维护的旧代码路径。**
- P1 **真实但对账可修复**：余额由"期初余额 + 流水"自动得出，所有账户同一套规则；对不上时提供校准手段（改期初），不引入"调整流水"类型。
- 不做：多币种、投资市值联动、云端账号、精细负债模型（远期 P3，本期明确不做）。

### 目标与非目标

| | |
|---|---|
| **解决的用户问题** | 月度"刷了多少/欠多少"心里有数；总可支配资金一目了然；月末对账（微信/支付宝账单 vs 本 App）；收入去向清晰 |
| **核心场景** | ①记账时选对账户 ②账户页看总余额与各账户余额 ③按账户核对流水 ④还款/挪钱用转账 ⑤账户管理（自建账户与类型标签、改名、合并、删除、排序） |
| **非目标（本期）** | 预算按账户拆分；按账户的统计图表；资产趋势图；多币种；对账单文件导入比对——列入 P2/P3 |

## 3. 用户故事（真实用户视角）

按"我作为用户"的真实使用习惯排序，标注频度（H=高频每次记账，M=每周，L=每月/偶尔）：

1. **[H] 记一笔支出时选对地方**：买咖啡 18 元走微信零钱、打车走支付宝、大件走花呗——选择器里是我自己建的账户池（含图标/颜色），不是两套互相打架的文案列表。
2. **[M] 账户记忆**：我连续几笔都从"微信零钱"出账，记账页默认就是它，不用每笔重选；偶尔换"信用卡"点一下即可。
3. **[M] 还款不虚增支出**：每月 8 号从储蓄卡还花呗 3,000，记为"转账"：本月支出统计、预算进度、复盘全部**不含**这笔 3,000；两个账户余额各自正确变化。
4. **[L] 对账**：月底把支付宝月度账单和 App 明细对照。在"支付宝"账户流水页看本月记录逐笔核对，漏记的补一笔、多记的删掉。
5. **[L] 欠款有数**：账户页里"花呗""信用卡"余额是负数（红字），打开就知道要预留多少还款。
6. **[L] 校准**：某个账户余额和银行 App 差 8 块钱（多半历史某笔漏记）。点"校准余额"把它掰回真实值，之后流水继续自动累计，明细里不出现"调整记录"。
7. **[M] 收入落位**：工资到"招商银行"、利息到"理财通"、报销到微信零钱——每笔收入有明确去向。
8. **[L] 自由管理**：升级后我的老数据按原样分成"微信支付""微信零钱"两个账户，我把它们**合并**成"微信"再改名，顺手把"银行卡"改名"招商银行"、换图标、排序；没流水的"其他"直接删除。
9. **[L] 自定义类型**：我把"押金"建成一个类型标签用于分组；App 不做"这算资产还是负债"的判断。
10. **[L] 换机/双机**：和家里另一台设备同步后，账户连同记录一起过去，不丢不重。
11. **[M] 老数据不糟心**：升级后我过去 800 笔记录自动归到同名账户下（当年没填支付方式的归入一个"默认账户"，可改名/合并）；老 CSV 导出件还能原样导入。
12. **[L] 到处搬家都成立**：CSV 导出去 Excel / 发微信、备份文件存文档目录、另一台设备同步——账户信息在每条链路里都完整往返（转账两条腿、账户本身不丢）。

## 4. 概念模型

### 4.1 账户（Account）——新增一等实体，全部字段用户自定义

| 字段 | 说明 |
|---|---|
| id / syncId(unique) / createdAt / updatedAt / deletedAt | 复刻 CategoryEntity 的同步骨架（syncId 稳定身份，软删墓碑），双机同步直接套用现有合并机制 |
| name | 用户自由命名，如"微信零钱""招商银行工资卡""花呗" |
| type | **可选自由文本标签**（如"储蓄""信用""投资""押金"）。**代码不读取它的值做任何分支、计算或特判**，仅用于账户页分组与展示 |
| iconName / colorHex | 复用分类图标/色板体系（CategoryIconHelper），纯外观 |
| openingBalanceCents | 期初余额（分，Long，可正可负）。余额引擎 = 期初 + 该账户历史流水 |
| isArchived / sortOrder | 归档隐藏；用户排序 |
| remark（可选） | 如"尾号 8848"、开户行 |

**不设**：类型枚举、内置类型列表、按类型区分的字段/规则。

**起步账户（唯一的内置行，非类型语义）**：参照"内置默认分类"的既有惯例（AppDatabase 18 支出 + 6 收入预置分类），新装与迁移后保证**至少存在一个账户**（默认名"默认账户"，用户可改名/合并/删除）。这是"每笔记录必有所属账户"（§4.2）的直接推论，不是对账户意义的任何判断。

### 4.2 记录侧改造：accountId 必填 + 转账类型（v6 表重建一并做干净）

- **`paymentMethod` 列删除**，替换为 `accountId`（NOT NULL，FK→accounts，RESTRICT，与 categoryId 现有模式一致）。**不留弃用列、代码无任何旧字段读写路径**；迁移与导入所需的"老文本 → 账户"只发生在 v5→v6 迁移或文件导入的边界（§7.1/7.2），v6 本体是干净的。
- `records` 表 v5→v6 **整体重建**（INSERT…SELECT 保数据），同时完成三处结构变更：删 paymentMethod、加 accountId（非空 + 索引 + FK）、加 toAccountId。
- **记录类型扩为 3 种**：`EXPENSE / INCOME / TRANSFER`（沿用 RecordType 枚举与字符串存储）。
- **转账 = 单条记录**：`accountId`（转出）+ `toAccountId`（转入）。**转账记录不挂分类：categoryId 改为可空，仅 TRANSFER 为空**（不再设计"隐藏转账分类"——它会污染分类管理/统计/同步/重置等一堆流程，可空 + 保存层校验 + 列表 LEFT JOIN 修正更干净）。EXPENSE/INCOME 的 categoryId 由保存层强制非空（UI 本就必选），统计口径不变。
- 一致性约束由保存层保证（Room 不做 CHECK）：TRANSFER ⇒ accountId ≠ toAccountId 且两者非空；EXPENSE/INCOME ⇒ categoryId 非空、toAccountId 为空。
- 期初/余额/总余额全部按"每笔必有账户"成立，无"未指定"漏网资金。

### 4.3 资金规则（唯一一套，对所有账户一视同仁）

- **唯一余额公式**（不分类型，无例外）：
  `余额 = 期初余额 + Σ入账(收入 + 转入) − Σ出账(支出 + 转出)`，结果**可正可负**。
- **负余额 = 用户自己口径下的欠款/透支**：由用户在期初或校准中录入（如"花呗"设期初 0，刷卡支出让它自然变负）。界面只做通用的负数红色排版，不做任何"这是信用账户"的判断。
- **总余额 = 全部账户余额之和**（含负值，自动冲减）。不拆"资金/负债"口径——拆分即要求代码理解账户意义，违背 P0。
- **预算、统计（收支/环比/占比）、复盘、小组件月汇总：只计 EXPENSE / INCOME，永远排除 TRANSFER**（记录类型语义，全链路一致）。
- **任何账户都可用于支出、收入、转账任一端**，无能力限制。
- 金额继续以"分"存储、方向由记录类型表达，与现有约定一致。

> 用户若把"还款"记成"储蓄卡支出 + 花呗收入"两笔，预算会虚增——完全自由模型下的用户选择；App 在帮助文案与转账引导中建议"还款请用转账"（§9 R6）。

## 5. 范围规划（分期）

### P1 —— 账户体系 1.0（本迭代，MVP）

1. **数据层**：AccountEntity + AccountDao；records v6 表重建（删 paymentMethod、加 accountId/toAccountId、categoryId 可空）；存量回填（§7.1）；TRANSFER 类型。
2. **记账页（支出/收入）**：两套硬编码列表退役 → 统一账户池选择器（图标+颜色+余额小字，支出/收入同一池不加过滤）；默认账户 = 最近使用（记忆）> 起步账户；快捷解析与账户名打通。
3. **账户页（替换占位页）**：总余额总览卡（总余额 + 本月流入/流出）；账户卡片流（按用户类型标签分组，负值红字，本月入/出小字）；管理（新增/编辑/合并到…/归档/删除-仅无流水/排序/校准余额）；**转账入口**（转出/转入/金额/时间/备注 sheet）。
4. **账户流水页**（二级 push，复用明细行组件，照 CategoryRecordsScreen 模式）：单账户 × 月视图，顶部余额 + 本月入/出——对账主战场。
5. **明细页筛选**：chips 由"支付方式"改为"账户"（全部账户 = 旧"全部"语义；每条记录必有账户，无空态分支）。
6. **数据链路全通（§7）**：CSV 导入导出、JSON 3.0、设备同步、DB 快照备份核对、"清空全部数据"重置账户。
7. **转账跨模块口径**：首页收支卡/预算/统计/复盘/小组件均排除 TRANSFER（§8 回归清单逐一核对）。

**P1 不做**：统计页账户维度图表、资产走势（→P2）；调整流水类型（校准替代）；对账单比对；多币种；账户类型的任何计算特判。

### P2 —— 账户洞察
统计页"账户"维度支出构成环形图；各账户/总余额按月走势（由流水推，无需快照表）；设置页补"默认账户"入口（顺手收编无 UI 的 defaultRecordType）；小组件可选显示总余额。

### P3 —— 远期候选（不承诺）
多币种与汇率；负债分期模型（需要类型语义，与 P0 冲突，用户明确要求再评审）；对账单导入勾对；按账户拆分同步（当前同步为整库合并）。

### 5.4 校准（对账兜底，P1 含）
账户页每账户"校准余额"：输入当前真实余额 → 差值并入期初（`openingBalance = 真实值 − Σ流水`），此后流水自动累计。明细无伪记录、统计不污染、幂等可重复；文案说明"差 N 元并入历史基线"。P1 不做撤销。

## 6. 关键 UX 规则

### 6.1 记账选择器（H 场景）
- 支出与收入共用**同一账户池、同一组件**，无类型过滤；文案统一叫"账户"（**待拍板 D1**），行内显示类型标签与余额。
- 列表按"最近使用 → 用户排序"；新增账户可在选择器内一步完成（名称即可，其余后补），保证首次记账不卡壳。
- 解析"咖啡15块花呗" → 自动带出花呗账户，零额外点击。

### 6.2 账户页信息架构
```
账户 (TopAppBar + 右侧"管理")
├─ 总余额总览卡（总余额 ¥x · 本月流入 ¥y · 本月流出 ¥z）— 不拆"资金/负债"
├─ 快捷动作：转账（醒目）｜ + 新建账户
├─ 账户列表（可选按用户类型标签分组；未填类型 → "未分类"组）
│   每行：图标色 · 名称 · 类型小字 · 尾注（本月入/出）· 余额（负值红字）
│   点击 → 账户流水页（对账）；菜单 → 编辑 / 校准余额 / 合并到… / 归档 / 删除(仅无流水)
└─ 空态仅出现在"账户被全部删除"的极端情况 → 引导重建起步账户
```

### 6.3 记账默认账户记忆
DataStore 存 `last_used_account_by_type`（支出/收入各一），保存成功时更新；无记忆时默认起步账户（**待拍板 D7**）。设置页 P1 不加"默认账户"项（P2 收编）。

## 7. 数据链路全通：迁移 · 导入导出 · 备份 · 同步（v1.2 重写）

**总原则**：v6 本体只认识账户；所有"老文本 → 账户"的转换只发生在三条边界——DB 迁移、CSV 导入、老同步对端，且**共用一个通用规则（§7.2 按名建档）**，v6 内部不存在任何兼容分支。

### 7.1 Room v5→v6（一次性迁移，启动自动备份快照兜底不变）

```
MIGRATION_5_6:
1. CREATE TABLE accounts（§4.1 schema；syncId 唯一索引；deletedAt 墓碑）
2. CREATE TABLE records_new（新结构：id/type/amount/categoryId 可空/accountId NOT NULL/
   toAccountId 可空/recordTime/remark/split* /createdAt/updatedAt/syncId unique/deletedAt
   + categoryId、accountId、toAccountId、recordTime、type、splitGroupId、syncId 索引 + FK）
3. 建档：对 records 中 DISTINCT paymentMethod（非空、去空白）逐值 INSERT 账户（name=原值）；
   若结果为空集（老数据全未填），INSERT 起步账户"默认账户"
4. 回填 + 搬数据：INSERT INTO records_new SELECT …（accountId 按 3 的映射；空值→起步账户）
5. DROP TABLE records；ALTER TABLE records_new RENAME TO records
6. 删除老表相关索引后按新表重建
```

原则：**不合并、不归类**。"微信支付"与"微信零钱"成为两个账户（是用户当年亲手选的词），合并与否交给用户（账户页"合并到…"）。升级后首开账户页引导："历史记录已按原支付方式分入同名账户，可改名/合并/校准。"

### 7.2 按名建档：老文本 → 账户的**唯一**通用规则

> 目标账户名不存在 → 新建账户（name = 该文本）；存在 → 复用。仅用于文件/旧数据边界（DB 迁移回填、CSV 导入），v6 运行时逻辑不出现。

CSV 导入因此**天然兼容老文件**：老导出件的"支付方式/方式/收付款方式"列头本就是账户列的字典同义词（CsvImportUtils.kt:254-255 现成 ColumnMap，仅表头映射，非代码债务）；值如"储蓄卡""招行"自动建档为用户可管理的账户（废除原"未知归'其他'"的丢语义行为）。**v6 导入器只有一条通用路径，不存在"老格式专用代码"。**

### 7.3 导入导出（CSV，用户可见的表格交换）

- **导出列调整**：`支付方式`列 → `账户`列（写账户名，转账行为转出账户）；新增 `转入账户`列（仅转账行有值）；`类型`列值域 支出/收入/转账。合计类行（若有）与统计口径一致排除转账。
- 转账行 CSV 往返：一行"转账"，账户=转出，转入账户=转入，金额为正；导出含备注与时间，与现结构同构。
- **导入规则**：账户列按 §7.2 按名建档（不存在的账户自动建）；转账行要求两个账户列都存在且不同，缺失/相同则跳过并计入失败清单（沿用现有导入结果提示）；EXPENSE/INCOME 行的 categoryId 归类逻辑不变。
- 往返无损承诺：导出 → 导入应等量同值（P1 验收用自动化/脚本抽验）。

### 7.4 备份 / 恢复（DB 快照，文件级）

- 设置页"立即备份到文档 / 从备份文件恢复"走 DatabaseBackupManager 的 **DB 文件拷贝**：账户表、新列、转账自动包含，**零代码改动**；v5 旧备份文件 → v6 打开时由 Room v5→v6 迁移链自然升级（同一迁移代码，已在 7.1 演练范围）。
- 启动/升级前自动快照自愈（AppDatabase.kt:102-129 现有机制）不变，覆盖 v6 迁移。

### 7.5 设备同步（JSON 交换格式 3.0）

- **JSON 格式升 3.0**（格式字段变化见下；开发期不再提供 2.0 读取器，v5 端老 payload 无法被 v6 解析时按协议报错并提示双方升级，不做静默降级容错）。
- 结构：`accounts` 数组 + `categories` + `records`；记录对象字段：**账户引用一律用 syncId**（accountSyncId / toAccountSyncId，与 category 的既有引用方式对齐——跨设备合并时按 syncId 解析为本地 id）；删除 `paymentMethod` 字段。
- **合并规则照抄 categories 的成熟模式**：accounts 按 syncId 插入/更新/墓碑（deletedAt）传播；合并顺序 = accounts → categories → records（records 的 accountSyncId 在合并时解析为本地 account id）。
- 记录指纹（SyncDao.kt:278-315）与 FamilySyncManager 版本指纹随 JSON 字段自动扩展；同步完成文案加"Z 个账户"。
- 双端 v6 起步账户 syncId 不同属正常现象（各自随机 UUID）：合并后出现同名双账户时，与"两台设备各自手建同名分类"现状行为一致，用户可自行合并，不做名称级魔法。
- 设备发现/配对/加密链路不动（FamilySyncManager/WifiSyncManager 只换 payload 结构）。

### 7.6 清空全部数据
现有行为（删记录 + 恢复默认分类 + 清快捷学习）扩展为：删除全部账户后重建一个起步账户，保持"每笔必有账户"不变量。

## 10. 验收清单（P1 Done 定义）

1. 老库升级：记录数/金额合计与升级前一致；每笔记录必有所属账户（无空值）；paymentMethod 已从 schema/实体/JSON/CSV 中彻底消失（代码 review 项）。
2. 支出/收入共用同一账户池，任何账户两端可选；记忆与起步账户默认生效；"咖啡15块花呗"解析带出花呗。
3. 预算/统计/复盘/小组件完全不含转账；转账后转出/转入账户余额各自正确、总余额不变；转账行无分类且列表正常显示（LEFT JOIN）。
4. 自建账户（任意名/类型标签）与任何账户行为完全一致——无因名称或类型不同而行为不同的代码路径。
5. 负余额红字；校准后差值并入基线、流水自动累计、明细无伪记录。
6. 合并账户：流水全转移、原账户删除、双机同步后正确传播。
7. 明细页按账户筛选；账户流水页可对账（左滑删除、点编辑）。
8. CSV：导出含账户列与转账双账户列；老 CSV（含"支付方式"列头）可导入且未知名自动建档；导出→导入等量无损抽验通过。
9. JSON 3.0 双机同步：账户+记录一致，归档/删除墓碑正确传播；双端均为 v6。
10. DB 快照备份/恢复在 v6 下往返可用；v5 备份文件可经迁移链恢复。
11. 快捷记账、跨月分摊（同账户多行分片）、隐私模式、清空全部数据（账户重置）等既有功能回归通过。
